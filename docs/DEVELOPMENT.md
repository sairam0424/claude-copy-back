# Development

Checked on 2026-10-25 with Node 26.9.0 (the test suite also on 22.23.2), Claude Code 2.1.310 and macOS. The commands below were run when this page was written, except the sealed-rig stages and the tools that read real data (they start Claude Code in a sandbox or touch your clipboard), which are documented from the scripts' own usage text, and the workflows' runs on GitHub, which are described under CI.

## Prerequisites

- **Node 22.19.0 or newer** to run the tests (`engines` in `package.json`). Type stripping is on by default from Node 22.18.0, and the timing helper of the tests (`tests/timing.ts`) calls `process.threadCpuUsage()`, which arrived in 22.19.0 (from the Node changelog). The suite was run on the maintainer's Mac on Node 26.9.0 and 22.23.2 (22.19.0 itself is not installed there). CI runs it on 22.19.0, 24.x and 26.x on Linux and on 22.19.0 and 24.x on macOS; its first run, on 2026-10-24 on the 0.1.0 tree, passed all five legs, so the floor has run on real runners. `npm test` passes the files as a quoted glob (`"tests/*.test.mts"`) because `node --test tests/` (a directory) does not work on Node 22. The node:test files are `*.test.mts`, not `*.test.ts`, on purpose: see the note under the gates table.
- **No `npm install`.** There are no dependencies and no lockfile. Everything imports a relative file or `node:*`.
- **Claude Code 2.1.299 or newer** for the engine gates (`kit-test.sh`, `check-footprint.sh`, `validate`). 2.1.292 and 2.1.296 refuse `$` across an import and 2.1.299 is the oldest version tried that accepts it (2.1.297 and 2.1.298 were not tried).
- `jq` for `kit-test.sh`, `shellcheck` for the shell scripts, a TypeScript compiler (optional) for `typecheck.sh`, and `actionlint` (optional) for the workflow files.
- **macOS, `tmux` and `python3`** for the sealed rig only. Nothing else in the repository needs them.

Run the tests with a scratch `HOME` and temp folder when you can: `env HOME=$SCRATCH/home TMPDIR=$SCRATCH/tmp COPY_BACK_TMP=$SCRATCH/tmp npm test`. No test reads the real clipboard, your transcripts or your home (both suites pass with an empty `HOME`), but the isolation costs nothing. `typecheck.sh` is the exception: it looks for a compiler under `$HOME/.npm/_npx`, so with an empty `HOME` pass `CB_TSC`.

## Layout

```
.claude-plugin/   plugin.json (the version lives here) and marketplace.json
.github/          workflows (ci.yml, engine-drift.yml), issue forms, the PR template, CODEOWNERS, Dependabot
hooks/            the runtime: hooks.json -> register.tsx; api.ts, cc.ts, input.ts, outcome.ts, run.ts
src/core/         the matcher: the lossless source match (19 files)
src/sim/          a screen simulator and a seeded PRNG, for tests and the replay harness
src/replay/       the offline replay harness and its comparator
src/captures/     the real-copy test tool (see "The captures tool")
scripts/          the gates, the replay entry and the captures entry; scripts/lib/ holds the source scanner
tests/            the node:test files (*.test.mts, including the manifest and workflow checks), the helpers (cc-fakes, cc-fixtures, cc-spies, timing) and tests/kit/, which holds the engine tests (*.test.tsx)
realrender/       the sealed live-test rig: entry points, lib/, tests/, RULE-3.md, and probe/ (a scratch plugin, never install it)
```

What the mod runs is `hooks/` plus `src/core/`: the hooks import `../src/core/*.ts`, and the source guard counts 25 files loaded (6 in `hooks/`, 19 in `src/core/`). The sealed rig loads a copy of `.claude-plugin`, `hooks` and `src` (59 files). The rest of the repository travels with a marketplace install but is never loaded.

A `/cc` run: `register.tsx` declares the command and answers `{}`; `run.ts` hands `cc.ts` the four engine calls (through `api.ts`); `cc.ts` reads the clipboard answer (`input.ts`), asks `findSource` in `src/core/match.ts`, writes the answer with `ui.copy` only on a match, and shows the counts-only line `outcome.ts` builds.

### Tests that bound time

Eight files guard against pathological slowness: `budget`, `limits`, `match-rules`, `fuzz`, `inline`, `review-wrong-slice`, `search` and `cc-source-scan`. None of them reads the wall clock (`tests/timing.ts`). Each asserts the answer first. `tests/budget.test.mts` also asserts the counters of the search meter, which fix how much work an input may cost (hits kept, candidate work, and the engine's own `indexOf` allowance, each spent in exactly the amount the limits in `src/core/search.ts` set). What is left of time is a sanity bound on CPU time, of the main thread or of a child process, set at many times the idle figure. It catches work that grows with the square of the input and loops that never end; it cannot tell twice as slow from as before. `CB_TEST_TIME_FACTOR=3 npm test` multiplies every bound by 3 for a slow machine, and `CB_TEST_TIME_REPORT=<file>` appends one JSON line per check to tune the bounds. `tests/budget.test.mts` runs its children with `--max-old-space-size=192` and a 120 second kill, so a regression cannot take the machine down.

Checked on 2026-10-24 on a 10-core Mac: five full suites started together, each in Node's default file concurrency (about 45 test processes), with eight CPU burners running, 5 of 5 passed (1352 of 1352 each, on that day's tree), and with six suites and sixteen burners (load average 62) 6 of 6 passed; the CPU time of the bounded checks rose at most 1.7 times. The same load on the previous tests: 5 of 5 failed, each on the "2000 identical table rows" test of `budget` (7.2 s against its 5 s wall-clock bound in the first run). `npm test` still runs the files one at a time.

### CI

`.github/workflows/ci.yml` is documented in its own header; the summary:

- **Every pull request, push and manual run (Linux):** the plain Node suites on Node 22.19.0, 24.x and 26.x, the replay self-test, `shellcheck`, the source guard, and an engine job (`claude plugin validate . --strict`, the footprint gate, the kit tests and `claude plugin test .`) on exact Claude Code pins, 2.1.299 (the floor) and 2.1.310 (what the 0.1.1 matcher was calibrated on). No model call, no login, no secret.
- **Pushes to `main` and manual runs only (macOS):** the suites on Node 22.19.0 and 24.x plus the rig's unit tests (`tests-macos`). Why not on pull requests: of the rig's tests only `realrender/tests/stub.test.mjs` needs macOS (Homebrew's `python3` and `/usr/sbin/lsof`, checked by grep on 2026-10-24); the rest use fakes. A pull request that touches `realrender/` runs `npm run test:rig` itself (the PR template asks), or the workflow is started by hand on its branch; the merge runs it again. Cost: macOS minutes count ten times on a private repo (2,000 included minutes a month on Free); standard runners are free on a public one. In the first run each macOS job took 18 and 25 seconds, about two billed minutes in all if GitHub rounds each job up to a minute (inference; the billing API reported zero for this repository). After the repository goes public the `if:` on `tests-macos` can go.
- **`ci-ok`:** the one check a branch ruleset should require. It runs even when a job failed or was cancelled (`if: always()`), reads `toJSON(needs)`, and passes only when every job finished as expected: success for all, and for `tests-macos` skipped on a pull request and success otherwise. A skipped job counts as passed on a required check (GitHub's table of skipped-but-required cases), which is why an unexpected skip fails here. Requiring the matrix job names directly would break whenever a matrix changes.
- **Not run in CI:** `typecheck.sh` (it needs a types file the engine writes only when a session loads the plugin-authoring skill) and the sealed live rig (maintainer's Mac only).

Hardening: read-only token, no secrets, no privileged trigger, every action pinned to a full commit SHA with its version beside it (both pins were checked on 2026-10-24 with `gh api` to resolve to the latest releases of `actions/checkout` and `actions/setup-node`), `persist-credentials: false`, a timeout on every job, a concurrency group, and no `${{ }}` inside a `run:` block. `tests/workflows.test.mts` pins these rules and that `ci-ok` waits for every job, and runs the `ci-ok` script itself on sample documents (all green, a failed job, a cancelled job, unexpected skips, macOS skipped or run on the wrong event, `{}`). The rest it reads as text, so it does not replace `actionlint`.

Checking a workflow change locally, the way CI runs it: `actionlint .github/workflows/*.yml` (with `shellcheck` installed it checks the `run:` blocks too); parse the files with any YAML parser; run each `run:` step from a clean checkout with `bash --noprofile --norc -eo pipefail`; run the engine job's commands with an isolated `HOME` and a stand-in `npx` that maps the pinned package spec to a cached build; and run the `ci-ok` script with sample `NEEDS_JSON` documents (the test does this; an empty `NEEDS_JSON` is not one of them and the script lets it pass, which GitHub's `toJSON(needs)` cannot produce). A real run on GitHub is the final test: none has happened for the changes of 0.1.1 at the time of writing.

### Engine drift check

The plugin API is early access, and `ci.yml` pins two exact versions. `.github/workflows/engine-drift.yml` runs every Monday (05:37 UTC) and on request: it asks npm for the newest published `@anthropic-ai/claude-code` once, checks that the answer is a plain `x.y.z`, installs exactly that version, and runs the strict validate, the footprint gate and the kit tests. It needs no key and makes no model call.

- **Who hears about a failure.** GitHub notifies the user who last edited the `cron:` line, and a failed run shows red in the Actions tab; whether an email arrives depends on that user's Actions notification settings, which this repository cannot set. Check them once. Scheduled workflows run only from the default branch and can be delayed at busy times; in a public repository GitHub switches them off after 60 days without repository activity (a push or the "Run workflow" button brings them back).
- **What to do when it is red.** (1) Open the run: the summary names the version and the failing step. (2) Reproduce it with an isolated `HOME` on a copy of the repository: `CB_CLAUDE="npx --yes @anthropic-ai/claude-code@X.Y.Z" bash scripts/check-footprint.sh` (and the same for `scripts/kit-test.sh`; `claude plugin validate . --strict` through the same `npx`). (3) A changed access report or plugin API means a fix in the mod or in a gate: a normal pull request, tests first. A harmless change means moving a pin in `ci.yml`. (4) If the mod must not be used with that version, say so in the README under Limits. (5) Start the workflow by hand to confirm the fix.
- **What it does not cover.** It checks that the mod still loads and passes the engine gates, not that the matcher's model of the drawing still holds: a new Claude Code can draw a reply differently, and only a sealed rig run (`modeldiff.mjs`, `capture.mjs`) shows that.

## Engine rules (learned the hard way)

The access report that `claude plugin validate` prints lists every engine call with the functions that call it, and it cuts a `calls` or `hooks` line near 980 characters, marking the cut `[+N chars]`. A cut report cannot show every call, and a catalogue publisher can hold a listing whose report is cut. So:

- **Engine calls go through `hooks/api.ts`.** One wrapper per API (`pbpaste`, `history`, `toClip`, `notify`), plus the one `$.command.register` call that `register.tsx` spells itself. The calls line is 130 characters today; the gate is 850.
- **Wrappers are function declarations**, with names of **at most seven characters**, unique across `hooks/` (`tests/cc-seam.test.mts` pins all three, `tests/kit/api.test.tsx` the length again). The engine follows `$` past an import only into a function declaration. An arrow function bound to a const holding `$` fails when the module loads. Engines 2.1.292 and 2.1.296 refuse `$` across an import at all, so the version floor enforces itself.
- **The footprint gate greps comments.** An engine call in the `$.<noun>.<fn>(` form anywhere in `hooks/` or `src/` outside `api.ts` and `register.tsx` fails the gate, a comment included. Describe the call in words.
- **A new engine call** means a new wrapper, a new entry in `EXPECTED_APIS` in `scripts/check-footprint.sh`, an updated Data handling section in the README and an updated table in [SECURITY.md](../SECURITY.md). It is a security change; do not add one casually.
- **State atoms** are not used by `/cc`. If you ever add some: the engine validates `read` and `update` against an atom made in the calling file, so declare the atom in every file that reads it (this rule comes from a sibling plugin and has not been exercised here).
- **The command name** `cc` is a literal in the declaration and in the hook filter. If another plugin registers `cc` later it replaces this one silently; a built-in's name is refused and the mod shows `could not register /cc`.
- **The hook never reads `next`** and answers `{}`. Anything it returned as `text` would be printed in the transcript and read by Claude.
- **Do not load the dev folder as a plugin.** The engine can write about 840 KB of type files (`.claude-plugin/types/`) and a `tsconfig.json` into a folder it loads. Both are in `.gitignore`. Load a copy of `.claude-plugin`, `hooks` and `src` instead, as the README says.

## Privacy rules for contributors

Clipboard text and message text never reach a toast, a log, a store, a state key, returned text, a thrown error or a file. Counts and words from fixed lists only: add a field to `Decision` in `hooks/outcome.ts` only if it is a count or a member of a fixed list. A toast line carries no plugin name (Claude Code adds `copy-back: `) and stays within `TOAST_MAX_CHARS` (45), so the reply number is visible at 60 columns; `tests/cc-outcome.test.mts` checks every line at the extreme counts. Never read the real clipboard in a test or a probe, never commit a real transcript, copy or screen capture, and never print one in a report. The layers that enforce this, and their limits, are in [SECURITY.md](../SECURITY.md).

The matcher's work is capped: at most 10,000 start positions per reply, 200,000 in all, 100 million characters of candidate work, and the engine's own `indexOf` only while its worst case fits a budget (otherwise a linear-time search). A copy in more places than that is refused as `ambiguous`. The caps do not make the total cost independent of the size of the replies: it grows with it. `tests/budget.test.mts` and `tests/search.test.mts` cover repeated rows and many candidate positions, not nested lists with a link and struck text on every line. A reply that holds both a link and struck text is searched under four drawings, so such input costs about four times what 0.1.0 did. Measured on a window of 40 replies of that kind (the final run for 0.1.1, heap capped at 1 GB; reported, not re-runnable from this repository): 8 MB in all took 5.6 s and 456 MB (0.1.0: 1.4 s and 243 MB), and 40 MB took 29.6 s and 1.67 GB (0.1.0: 7.5 s and 601 MB); plain prose of 8 MB takes 0.7 s. A real reply is far smaller (the largest output is about 0.5 MB), and only the newest 40 replies are searched.

## The sealed live rig (`realrender/`)

The offline tests cannot prove that the matcher's model of the screen is right, because the matcher and the simulator share one model. The rig closes that gap without spending money or touching your clipboard.

**What it does.** It resumes a **synthetic** session in the installed Claude Code, inside `tmux` on a dedicated socket (`cbrender`), under `env -i` with an isolated `HOME`, a dummy credential and a stub API on `127.0.0.1` that answers 401. It loads a copy of the plugin with `--plugin-dir`, types `/cc` for each planned case, and reads the result from the screen and from the stand-in clipboard. It runs whichever `claude` comes first on `PATH` and records the banner version without enforcing it. Run the live stages (`live.mjs`) with your real `HOME`: the `deny-write-home-in` control breaks under an isolated one. The capture launches (`capture.mjs`, `rig.mjs`) may use an isolated `HOME`. It writes `{"tui": "default"}` into the throwaway settings (`realrender/lib/live-fixtures.mjs`), so every live launch draws Claude Code's classic display; the fullscreen display, which a clean profile started in on 2.1.309 with mouse tracking on, was never run live.

**Stand-ins.** The `pbpaste` stand-in prints a fixture the case chose (modes: the fixture, exit 1, sleep, a 5 MiB answer); `pbcopy`, `xclip`, `xsel`, `wl-copy` and `osascript` keep what they receive inside the throwaway folder and log a name, a byte count and a short hash. The shim folder is first on the sealed `PATH`.

**The Seatbelt profile** (`realrender/lib/seatbelt.mjs`, run with `sandbox-exec -f`): everything allowed by default, then no outbound network except addresses local to the host and unix sockets, no `mach-lookup` of `com.apple.pasteboard.1` (so even `/usr/bin/pbpaste` called by absolute path cannot reach the real clipboard), no write anywhere under the real home, and no read of the folders that hold credentials, settings, transcripts and your captures. `live.mjs controls` proves each of these from inside and outside the sandbox (13 controls) before any case runs.

**Why the real clipboard is never read.** Inside the sandbox it cannot be: the pasteboard service is refused and the shims stand in. The only code that reads the real clipboard is the optional `live.mjs clip` stage, which pipes `pbpaste` into `shasum` and stores only the hash, and `clipboard-hash.mjs` refuses a third read before anything runs. Equal hashes before and after a pass rule out text appearing on the clipboard, and only if there was text to compare: when the clipboard holds no text, both hashes are the SHA-256 of empty input. Up to 0.1.1 the read ran under plain `sh`, whose pipeline reports only the status of its last command, so a `pbpaste` that failed gave that same value with exit 0 and could not be told from an empty clipboard; both hashes of the 0.1.1 live pass were the hash of empty input (reported), so that pass shows only that no text appeared. The read now runs under `set -o pipefail` (`runHashPipe` in `clipboard-hash.mjs`), so a failed read throws and still counts as one of the two reads. Run `clip` yourself, once before and once after.

**The Warp profile.** `--profile default|warp` on `rig.mjs`, `capture.mjs` and every `live.mjs` stage makes the rig pretend to be a terminal. `warp` adds exactly `TERM_PROGRAM=WarpTerminal`, a Warp version string and `COLORTERM=truecolor` (`realrender/lib/profile.mjs`); `default` adds nothing. A static read of the installed Claude Code 2.1.310 binary found that Warp is recognised by `TERM_PROGRAM` alone (it enters the hyperlink list and the strikethrough set; the binary holds no `WARP_` name), so a link is drawn as its label and struck text without tildes. The Warp-like drawing is not specific to Warp: a review's static read of the same binary lists many other terminals on that path (the strikethrough test is false only for Apple_Terminal and `TERM=linux`), and one rig run with `TERM_PROGRAM=iTerm.app` at one width drew exactly what the Warp profile draws (reported; the iTerm profile was only in a scratch copy of the rig). The same two behaviours can be switched by user settings, so all four drawings can occur on a real machine, and the matcher searches all four. The profile is recorded in every evidence file, and a live pass has one profile (`summary` refuses a mix). Under `--profile warp` all 13 sandbox controls held.

**How to run it** (from the repository root, on a quiet machine; each stage is its own command so a long one can run in the background):

```bash
node realrender/gen-live-set.mjs --seed N --out SET [--family C]  # a new synthetic case set (40 replies, 160 spans); C has links, strike and nested lists
node realrender/live.mjs controls --out OUT                       # the 13 sandbox controls
node realrender/live.mjs clip --out OUT --label before            # optional: the only read of the real clipboard (hash only) ...
node realrender/live.mjs width --width 80 --out OUT --holdout SET # one launch; repeat for 60, 100 and 120
node realrender/live.mjs turn --out OUT                           # the control launch: unicode probe and "no model turn" check
node realrender/live.mjs clip --out OUT --label after            # ... and the second and last read
node realrender/live.mjs summary --out OUT --rule-version 2       # applies the frozen rule
```

Add `--profile warp` to `controls`, `clip`, `width` and `turn` alike for a pass in the Warp drawing. Use a new seed for every pass: the case set of a counted pass is never reused. `--holdout SET` is required. `--limit N` caps the number of cases of a launch, but **`--limit 0` is treated as no limit**, so it runs every case: do not use it as a dry run. Keep `OUT` and `SET` outside the repository.

**How long.** One width launch (48 cases) took about 4 to 5 minutes. The counted pass (four widths plus the control launch, with the two clipboard hashes around them) took 17 minutes from the first hash to the last.

**It is sensitive to load.** The plugin reads the clipboard with a 2 second limit. The `pbpaste` stand-in is a shell script that runs several programs; on a loaded machine (swap nearly full, a long `tar` running) it stalled for 2 to 8 seconds, and in two sanity launches 3 of 80 copies were refused with "could not read the clipboard", which the rig scores as wrong toasts. The refusal is the designed, safe outcome, but the launch is then not clean. Wait for a quiet machine before a counted pass.

**The frozen pass rules** are in `realrender/lib/live-rule.mjs` (nine conditions) and `live-rule-2.mjs` (twelve), fixed in code before any case ran and pinned by tests. A pass needs all of: the plugin loads and `/cc` runs; no model request and no assistant record added; at least 90 percent of valid positives exact, over all four widths and all 13 construct classes, with non-ASCII payloads; zero wrong payloads; refusals leave the clipboard untouched; toasts hold counts only and a planted canary string is absent; the sandbox controls hold; no non-local socket in any `lsof` sample; the real clipboard hash is unchanged and exactly two reads were taken; a positive control (the stub log is empty after the `/cc` cases and non-empty after an ordinary prompt); and a unicode probe (every case exact, with an em dash and a zero-width joiner among the payloads). Never edit a rule after you have seen results.

**Side effects to know about.** The rig writes `/tmp/cbrender.*`, `/tmp/cbctl.*` and `/tmp/cbcombo.*`, starts a tmux server on the `cbrender` socket and a loopback Python stub, and moves its scratch folders to `~/.Trash/` with `mv` when it finishes. `live.mjs controls` makes connection attempts on purpose: one from **outside** the sandbox to `192.0.2.1:9` (a documentation address; a real packet leaves the machine and times out) as a contrast control, and two from **inside** it, to `192.0.2.1:9` and `1.1.1.1:443`, which the profile must deny. If the profile ever failed, the second would reach a public host; the control exists to show that it does not.

The other entry points: `rig.mjs` (one sealed launch and a screen capture), `capture.mjs` and `measure.mjs` (capture a synthetic set at four widths and score it against the matcher; a holdout is scored once), `modeldiff.mjs` and `surveydiff.mjs` (diff the matcher's model of every reply against the real screen), `survey.mjs` (glyph and margin survey), `probe.mjs` and `probe-after.mjs` (check how the engine hands a mod its rows, using the scratch plugin in `realrender/probe/`).

**The screen-matching proxy and rule 3.** Between the offline tests and a live pass there is a cheaper check that needs no `/cc` run and no stand-ins. `capture.mjs --family A|B|C --seed N --profile P --out DIR` shows a synthetic 40-reply window in the real Claude Code at 60, 80, 100 and 120 columns and keeps the screens (about 20 seconds per width). `measure.mjs --set DIR --role calibration|holdout --seed N --per-width 60 [--rule 3 --profile P --freeze FILE]` cuts copies from those screens with a model of a terminal selection and scores the matcher on them. Family C (`lib/templates-c.mjs`) is the realistic one: inline markup inside list items, headings and quotes; inline, reference and auto links; struck text; nested ordered and mixed lists; long code lines; wide characters; about 10 percent unique tokens; repeated phrases; in-window twin messages; no tables. The tools around it: `modeldiff.mjs --hunks` lists every difference between the matcher's model and the real screens (it refuses a holdout); `freeze.mjs --out FILE` records the digests of the rule files, the generator, the matcher and the plugin tree with the recipe of each digest inside the file, and `freeze.mjs --verify FILE` recomputes them; `rescore.mjs` re-scores saved sets with the matcher in this checkout; `tokenfree.mjs` copies the words between two tokens so that twins and repeated phrases compete (never a tuning aid; it refuses a holdout unless `--after-verdict yes`); with `--gate yes` it is the never-guess gate described under rule 3 and exits 1 on any wrong or picked-wrong answer. The rig keeps a copy of the toast grammar in `realrender/lib/toast.mjs`; it must follow the wording in `hooks/outcome.ts`, or the rig scores every toast as wrong.

**Rule 3** (`realrender/lib/rule3.mjs` for the numbers, `realrender/RULE-3.md` for the words) judges one terminal profile on a fresh holdout of at least 120 captures: at least 95 percent exact, at least 80 percent for every class with 10 or more captures (links and struck text are classes of their own), no wrong slice, no false positive on either negative control, at least 10 matched and right, and the same on the padded variant. The Warp profile and the default profile are each judged; a holdout is scored once; the verdict is INCONCLUSIVE if the matcher that scores is not the one recorded in the freeze file. It was written and hashed before any family C screen was captured. The hash was recorded at 2026-10-24 14:21:49 UTC in a file that is not in this repository, so the timing is a report; the values are checkable:

```
ec9ad585f6053c8da6a40bdd09a97b9f15426e97093400103aa223e7f87716c3  realrender/lib/rule3.mjs
e0a54bbcd6440aa188a8234128d72e9eb7297994bc78ecb2c7f2f43587f0558f  realrender/RULE-3.md
```

**What rule 3 does not judge: whether the matcher refuses when it should.** Every capture of rule 3 holds a unique token, so no capture can be ambiguous, and a matcher that never refuses an ambiguity (it takes the newest candidate) passes rule 3: in the 0.1.1 review such a scratch matcher scored 240 of 240 with no wrong slice and no false positive (reported). Rule 3 judges how Claude Code draws a session and whether the matcher's model of the drawing agrees. The never-guess property is carried elsewhere: by the unit tests (the same scratch matcher fails 24 of them, VERIFIED on 2026-10-25) and by the **never-guess gate**, which is on the release checklist. The gate runs `node realrender/tokenfree.mjs --set DIR --gate yes` on a saved set: the copies are the words between two tokens, so twins and repeated phrases compete, and it exits 1 if any answer is wrong or is a pick of the wrong message among several that hold the words. Its floors (1,000 cases, 100 of them with a competitor) only stop an empty set from passing. A refusal where the screen could not tell is always acceptable; a pick that lands on the right text is acceptable. The gate is a regression gate on synthetic sets that live outside this repository, not a proof for real replies.

If `shasum -a 256 realrender/lib/rule3.mjs realrender/RULE-3.md` prints other values, the rule moved after data existed: say so and write rule 4. One disclosure: before the rule was registered, the generator's tests built the corpora of the two holdout seeds in memory (token statistics only, no screen, no matcher) and one generator constant was tuned after those figures had been seen; the tests were then moved to neutral seeds. The holdouts (seed 5202, Warp profile; seed 5303, default profile) were scored once each on Claude Code 2.1.310, 240 of 240 exact with no wrong slice and no false positive (reported). That checks how Claude Code draws a session, not what Warp copies, and not `/cc` itself.

## The captures tool and the frozen real-copy rule

`CAPTURES.md` is the maintainer's own acceptance test: about 20 real copies from a real terminal (the maintainer uses Warp), each judged by hand, scored by `node scripts/captures.mjs tally`. It is the one test that can say whether the matcher's model of a real terminal's copies is right. It has not been run yet.

- `node scripts/captures.mjs add | run [--show] | tally [--json]`, with `--dir`, `--root` and `--messages`. `add` reads the clipboard once; `run` and `tally` print counts and ids only; `run --show` is the only command that prints text, and it refuses unless its output is a terminal. Never run `add` or `run --show` from an agent or a script, and never type `run --show` inside Claude Code or with a leading `!`.
- **The rule.** PASS needs at least 20 judged copies, at least 70 percent of them `ok`, at least 10 of them matched and right (the tool returned text and you judged it `ok`; refusals judged right do not count toward the 10), no dangerous result (a `bad` verdict where the tool returned text) and nothing unresolved. The checks run in a fixed order and the first that applies decides: a dangerous result is a FAIL at any count; then anything unresolved is INCOMPLETE; then fewer than 20 judged is INSUFFICIENT; then under 70 percent is FAIL; then fewer than 10 matched and right is INSUFFICIENT; otherwise PASS. A FAIL is final by convention: do not add copies to turn it into a pass.
- **Frozen on 2026-10-23, before any real copy existed.** The verdict is decided by `decide()` in `src/captures/tally.ts`, and the numbers (20, 10 and 0.7) are pinned by a test. The SHA-256 of that file at the freeze:

  ```
  1ff524a3e8efab440f40b33a03fad818e15eb195883198c4b50f95b937b11024  src/captures/tally.ts
  ```

  After your copies are judged, `shasum -a 256 src/captures/tally.ts` must print the same value, and `git log --follow -p -- src/captures/tally.ts` must show no commit after the date of your first capture. Either difference means the rule moved after data existed. The wording around the rule (`tally-format.ts`, `tally-notes.ts`, `help.ts`, `CAPTURES.md`) was frozen at the same time. For publication two of those were edited in small ways, `help.ts` (two phrases that named Warp) and `CAPTURES.md` (one line that named the maintainer's folder); `tally-format.ts` and `tally-notes.ts` are byte-identical to the freeze. Only `tally.ts` decides the verdict.
- **Do not tune the matcher on those copies** before you have read the verdict.

There is a second, older "K1": `npm run k1` (`scripts/replay.mjs`) scores the matcher against a simulated screen built from your own transcripts. It can only agree with itself, which is why the real-copy test and the rig exist. It reads `~/.claude/projects` and prints one JSON document of counts.

## Release process

1. Work on a branch in a git worktree, tests first. A change under `hooks/` or `src/core/` changes the runtime and needs a new counted sealed live pass before a release; do not change the 2000 ms clipboard timeout in `hooks/api.ts` casually. **0.1.1 changed both, and its pass ran on 2026-10-24** on Claude Code 2.1.310 (reported; the plugin folders `.claude-plugin`, `hooks` and `src` were checked against the pass's freeze record on 2026-10-25 and are unchanged). Any later change under those folders needs another pass. That pass used a rule of its own (rule 3, revision 2: 95 percent exact, the Warp set rebuilt from the spans the screen shows, a clipboard bracket that held a writing stand-in for the plugin) which is kept in the maintainer's report folder and **not in this repository**, and `live.mjs summary --rule-version 2` was not used. Before the next pass port that rule and the set builder into `realrender/` with tests. To run a pass with the stages here: generate a family C set (`gen-live-set.mjs --seed N --family C`), run `controls`, `clip` (before), the four `width` launches, `turn` and `clip` (after) with `--profile warp`, then `summary --rule-version 2`, on a quiet machine, with the toast grammar in `realrender/lib/toast.mjs` already matching `hooks/outcome.ts`. The Warp drawing hides link destinations, so a stock set can lose 1 to 3 of its 40 spans per width: check how many spans are on the screen first (`capture.mjs`). The final run of a release must also include a fresh sealed sanity launch of the exact tree that will be tagged.
2. Run every gate above (including `actionlint` when a workflow changed), run the never-guess gate (`node realrender/tokenfree.mjs --set DIR --gate yes`) on the calibration set of each profile and on every holdout whose rule verdict is recorded (`--after-verdict yes`), and get an independent review of the diff. A wrong or picked-wrong answer blocks the release. Start `engine-drift.yml` by hand and check that it is green.
3. The version lives in **`.claude-plugin/plugin.json`**, and `package.json` carries the same string (`tests/manifest.test.mts` fails if they differ, or if the newest `CHANGELOG.md` section or its compare links do not match). The marketplace entry carries none: the engine would silently use `plugin.json` and `validate` flags a mismatch. Move `[Unreleased]` in `CHANGELOG.md` to `[X.Y.Z] - date` (the day the tag is cut; the release script sets it), update the compare links, and check that the README status line, Limits, the test and file counts (README, this page, `SECURITY.md`, `CHANGELOG.md`) and the supported versions in `SECURITY.md` are still true.
4. Commit as `chore(copy-back): release X.Y.Z`, fast-forward `main`, and create an **annotated** tag: `git tag -a vX.Y.Z -m "copy-back X.Y.Z: <one line>"`. (`claude plugin tag` would create a `copy-back--vX.Y.Z` tag instead; this repository uses plain `vX.Y.Z` tags.)
5. The maintainer pushes by hand: `git push origin main --follow-tags`. Then check that `ci-ok` is green on the pushed commit (the push runs the macOS legs too) and that the tag is annotated: `gh api repos/sairam0424/claude-copy-back/git/ref/tags/vX.Y.Z --jq .object.type` prints `tag`.
6. Create the GitHub release from the tag that exists: `gh release create vX.Y.Z --verify-tag --title "copy-back X.Y.Z" --notes-file NOTES.md` (add `--prerelease` while the project is experimental; `--verify-tag` aborts instead of creating a lightweight tag if the push has not happened). The notes are the CHANGELOG block plus an Install and Update line and a Verification block that says what was **not** verified.

A GitHub release is for people reading; `claude plugin update copy-back@claude-copy-back` follows the `version` in `plugin.json` on the repository.

The history starts at 0.1.0. The matcher, the replay harness, the captures tool, the rig and the plugin shell were developed before it, outside git.

Commits use Conventional Commits scoped `copy-back` (`fix(copy-back): ...`), with the reason in the body and no `Co-Authored-By` trailer. See [AGENTS.md](../AGENTS.md) and [CONTRIBUTING.md](../CONTRIBUTING.md).

## Before the repository goes public

The repository is private. Before it is made public, in this order: re-audit the whole history (no work e-mail, no local path, no key, no real transcript or clipboard text; `gitleaks git` over all commits); check that the README status line and Limits are still true and that `SECURITY.md` has a contact route you accept publicly; make sure `CODE_OF_CONDUCT.md` (Contributor Covenant 2.1 with its attribution section, reports routed like security reports) is on `main`; make sure the last `ci-ok` is green on the exact commit. After the flip: switch on private vulnerability reporting, secret scanning and push protection; require the single check `ci-ok` in a ruleset (not the matrix job names); remove the `if:` on `tests-macos` so macOS also runs on pull requests (macOS minutes are free on a public repository); and note that issue-form `required` fields, which GitHub enforces only on public repositories, start to apply, and that GitHub switches scheduled workflows off after 60 days without repository activity.
